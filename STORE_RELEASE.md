# FitFlow Release Guide

FitFlow uses one React/TypeScript codebase for Web, iOS, and Android through Capacitor. Native projects are included; signed binaries and store publication are separate, owner-controlled release steps.

## Prerequisites

- Node.js 22 or newer; install the exact locked dependencies with `npm ci`
- iOS: macOS and Xcode 26 or newer; this project uses Swift Package Manager, so CocoaPods is not required
- Android: Android Studio 2025.2.1 or newer, Android SDK platform 36, and JDK 21; the included Gradle wrapper selects Gradle 8.14.3
- Internet access on the build machine for Gradle/Maven and Swift package resolution on their first run

Review [Capacitor environment requirements](https://capacitorjs.com/docs/getting-started/environment-setup) when upgrading Capacitor. Do not silently change app identifiers, release signing, or SDK versions as part of synchronization.

## Manual verification and synchronization

```bash
npm ci
npm run check
npm run native:sync
```

These are manually invoked checks. No GitHub Actions or automatic CI workflow is included.

`native:sync` builds the Web bundle, copies it into both checked-in projects, and updates native plugin references. Rerun it after Web changes or dependency updates. It does not compile an APK, AAB, or iOS application, and does not resolve every native SDK dependency.

Do not run `native:add:*` in a normal checkout. Those commands only create a previously absent platform. Recreating these directories would lose project-level changes, including privacy resources, backup exclusions, artwork, and release version settings.

## Application identity and version

- App name: FitFlow
- iOS bundle ID / Android application ID: `com.fitflow.app`
- App version: `3.0.0`
- Native build number / Android version code: `1`
- Web output: `dist`
- iOS project: `ios/App/App.xcodeproj`; target and shared scheme: `App`
- iOS deployment target: 15.0
- Android minimum SDK: 24; compile and target SDK: 36

Before a later store upload, increment Android `versionCode` in `android/app/build.gradle` and iOS `CURRENT_PROJECT_VERSION` in Xcode. Update `versionName` / `MARKETING_VERSION` together with the package version. Check current store SDK requirements at release time.

## Android manual build

```bash
npm run native:sync
npm run native:open:android
```

Select the installed JDK and SDK in Android Studio, allow the Gradle sync to finish, and build there. On an already configured build machine, the command-line equivalents are:

```bash
cd android
./gradlew :app:assembleDebug
./gradlew :app:bundleRelease
```

Use `gradlew.bat` on Windows. `assembleDebug` creates a development APK using the standard debug signing flow. The release bundle requires the owner's upload-key configuration before it can be published; no signing credentials are included or generated by this repository. Keep `local.properties`, keystores, passwords, and `key.properties` out of version control. The commands above are instructions, not evidence that a build has passed.

## iOS manual build

```bash
npm run native:sync
npm run native:open:ios
```

Let Xcode resolve the Swift packages, select the `App` scheme, and test on a simulator. On a Mac with the matching simulator SDK, a simulator build can also be requested with:

```bash
xcodebuild -project ios/App/App.xcodeproj -scheme App \
  -configuration Debug -sdk iphonesimulator \
  -destination 'generic/platform=iOS Simulator' CODE_SIGNING_ALLOWED=NO build
```

For a physical device or release archive, the owner must configure the intended Apple team, signing certificate, and provisioning profile. Review signing and the bundle identifier in Xcode before archiving. Store upload is not part of the preparation commands.

## Security and privacy review

- `ios/App/PrivacyInfo.xcprivacy` is explicitly included in the Xcode app target's Copy Bundle Resources phase
- Android references `network_security_config.xml`, disallows cleartext HTTP, and trusts system certificate authorities
- Android automatic cloud backup and device-to-device extraction are excluded for the app's data; uninstalling can permanently remove local records, so do not rely on system backup
- Service workers are enabled only for production Web, using Capacitor runtime detection so Android's HTTPS WebView cannot be mistaken for a browser
- Status bar settings match the light page background; Android 15/16 edge-to-edge behavior relies on the app's safe-area layout, not legacy status-bar background settings
- Native launcher icons and splash screens use the existing `public/icon.svg` FitFlow design

The application does not send fitness data to a server. OS/browser-level backup behavior is separate from app-level sharing; review it on the actual release devices. Review `PRIVACY.md`, the installed plugins' privacy manifests, and store privacy declarations together. Replace the legal contact placeholder before publication. Do not claim health integrations, analytics, or data collection that this build does not implement.

## Required device acceptance

On both iOS and Android, check:

1. Cold launch, first-run onboarding, keyboard handling, rotation, safe areas, and accessibility text sizes
2. Workout start, pause/resume, background/foreground, app restart, recovery, completion, and repeated taps
3. Android Back navigation, connectivity changes, haptics, and light/dark system appearance
4. Profile/history/weight persistence through restart and update; reset/delete confirmations
5. Offline use after installing the bundle
6. Backup file import through each platform's document picker, native Web Share export where supported, and the copyable JSON fallback (including cancellation and clipboard denial). The Web edition has a separate data store and cannot retrieve native-only records. Native import/export has not been established by a Web test
7. Correct launcher/launch artwork and readable system bars on small phones and tablets

Do not label a build store-ready until actual native compilation, these device checks, accessibility review, and the owner-controlled publication details are complete.

## Owner-provided publication details

- Apple Developer Program and App Store Connect access, app record, distribution certificate, and provisioning profile
- Google Play Console access and intended Android upload signing key
- Final legal business name, support email, privacy-policy URL, and contact details
- Screenshots from the actual native build, descriptions, pricing, territories, and age-rating answers
- Current store policy, privacy, and SDK-requirement review

Never commit credentials, accept new account agreements, or upload a store build as an incidental part of source-code preparation.

## Web / Coolify
